RecallSoro 的核心不是“竞赛管理”或“旅行相册”，而是你的个人经历总入口。任何照片、文件、聊天截图、文字、链接和临时回忆都先进入统一收件箱。系统在后台提取线索，你有空时再把它们整理成经历、集合和模板视图。

- 先接住资料，减少四处归档。
- 原始资料永远保留，后续识别可以反复运行。
- 一条资料只保存一份，关系和视图可以有很多份。
- 自动整理只提出建议，不替你决定事实。

## 1. 先收集，再整理 {span=2}

```flow
任何入口 -> 统一收件箱: 上传、拖拽、手机分享、快速记录
统一收件箱 -> 自动提取: 时间、地点、文字、人物、文件类型
自动提取 -> 线索与建议: 可能的经历、重复项、待确认信息
线索与建议 -> 你的确认: 接受、修改、忽略、稍后处理
你的确认 -> 个人经历库: 形成事件、关系与模板视图
```

收件箱要允许“只有一个文件”“只有一句话”“只有一张照片”这类不完整输入。你不需要先决定它属于竞赛、旅行、课程还是生活记录。系统先记录来源和时间，再等待更多资料把它们连接起来。

## 2. 用四层数据保存完整经历 {span=2}

| 层 | 对象 | 保存什么 | 关键规则 |
| --- | --- | --- | --- |
| 原始层 | Capture | 原文件、原图片、原文字、来源、上传时间 | 不覆盖，不因归档变化而丢失 |
| 事实层 | Fact | 拍摄时间、地点、OCR文字、人物、文件摘要 | 标记来源和置信度 |
| 经历层 | Experience | 一次旅行、一次比赛、一次课程或一段生活经历 | 允许时间不精确 |
| 展示层 | Collection / View | 竞赛卡片、旅行时间线、年度回顾、自定义模板 | 只保存关系、筛选和布局 |

`Capture` 解决“我现在只想把东西放进去”。`Fact` 解决“系统从文件里读到了什么”。`Experience` 解决“这段资料讲的是哪一次真实经历”。`Collection` 和 `View` 解决“我想用什么方式回看它”。

一张照片可以只保存一个 `Capture`，同时通过关系出现在“杭州旅行”“2026 年回顾”和“个人摄影记录”里。模板字段只保存额外信息，例如竞赛中的队伍和奖项，旅行中的交通和住宿。

## 3. 你真正需要的页面

| 页面 | 作用 | 你会怎么用 |
| --- | --- | --- |
| 统一收件箱 | 放入还没整理的全部资料 | 批量拖入照片、文件、文字和链接 |
| 个人时间轴 | 按时间回看所有经历 | 从某年某月开始浏览和筛选 |
| 经历工作台 | 把零散资料组成一次经历 | 补充标题、时间、地点、人物和描述 |
| 素材库 | 找到原始文件和派生信息 | 搜索、预览、下载、查看来源 |
| 模板中心 | 创建竞赛、旅行或自定义模板 | 配置字段、卡片、时间线和筛选规则 |
| 智能收件箱 | 处理系统建议 | 批量确认归类、合并重复项、延后处理 |
| 回顾与导出 | 生成年度回顾或可迁移资料 | 导出 Markdown、JSON、ZIP 或 PDF |

首页不应该要求你先选择“竞赛”或“旅行”。首页只需要提供一个醒目的“放进去”入口、最近资料、待确认建议和时间轴。

## 4. 如何保证“只存一份”

系统为每个上传文件计算内容哈希。相同文件再次上传时，只增加一条来源记录，不重复保存二进制内容。相似但内容不同的照片可以由感知哈希标记为“可能重复”，由你决定合并还是保留。

删除某个模板或经历时，只解除关系。系统不会顺手删除原文件。原文件、提取结果、用户修改和归类关系都需要有审计记录，方便你回到最初状态。

## 5. 自动整理的正确边界

自动整理分为三类。第一类是确定性提取，例如 EXIF、文件名、PDF 文本和 OCR。第二类是候选匹配，例如“这几张照片可能属于同一次旅行”。第三类是用户确认后的关系写入。

```flow
上传资料 -> 确定性提取: EXIF、OCR、文本、哈希
确定性提取 -> 候选匹配: 时间相邻、地点相近、关键词相似
候选匹配 -> 智能收件箱: 说明命中依据
智能收件箱 -> 用户确认: 接受、修改、忽略
用户确认 -> 经历关系: 建立或解除关系
```

每条建议要能解释依据，例如“拍摄时间相隔 2 小时，地点都在杭州，照片中出现同一赛事名称”。模型不能覆盖原始文字，不能擅自把不确定的日期改成精确日期，也不能把猜测写成事实。

## 6. 设计时必须处理的问题

| 问题 | 实现方式 |
| --- | --- |
| 经历很多，分类会越来越乱 | 用自由标签和关系组合，模板只做视图，不建立硬编码目录 |
| 一次经历的时间可能记不清 | 支持精确日期、月份、年份、时间区间和“待确认” |
| 图片和文件来源复杂 | 保存来源、导入时间、哈希、原文件名和版本 |
| 自动识别会出错 | 建议进入收件箱，必须经过确认才能改变关系 |
| 个人数据不能丢 | 原文件备份、数据库备份、ZIP 全量导出和可迁移 JSON |
| 未来会换设备或换软件 | API 与导出格式稳定，数据结构带版本号 |
| 一开始不想配置很多东西 | 新建后即可上传，模板和标签都可以后补 |
| 全部资料可能越来越多 | 时间、全文、地点、人物、标签和关系组合检索 |

“全部经历”不代表系统能自动知道你人生中发生过什么。它需要有一个低摩擦的快速记录入口，例如输入一句“2026 年 3 月参加了某场活动”，之后再把照片和文件补进来。

## 7. 推荐的第一版技术结构

| 层 | 推荐方案 | 责任 |
| --- | --- | --- |
| Web / PWA | Next.js + TypeScript | 收件箱、时间轴、编辑器和模板页面 |
| API | FastAPI 或 NestJS | 鉴权、上传、对象、关系和导出接口 |
| 主数据库 | PostgreSQL | Capture、Fact、Experience、Template、Relation |
| 文件存储 | S3 兼容存储 | 原图、视频、PDF 和缩略图 |
| 异步任务 | Redis + BullMQ 或 Celery | OCR、缩略图、哈希、索引和候选匹配 |
| 搜索 | PostgreSQL 全文检索起步 | 关键词、全文、时间、地点和标签 |
| AI | OCR、文本分类、图像标签、候选聚类 | 只生成解释清楚的建议 |
| 安全 | 单用户账户、加密传输、备份和导出 | 保护个人资料并保持可迁移 |

第一版不需要先做复杂知识图谱，也不需要让模型自动写完整人生故事。先把“随时放进去、以后找得到、关系能补充、模板能回看”做好，系统就有持续使用价值。

## 8. 最小可行版本的开发顺序

```timeline
统一收件箱 | 上传图片、文件、文字和链接，生成 Capture | 第一阶段
个人时间轴 | 按时间查看原始资料和未整理内容 | 第二阶段
经历工作台 | 将 Capture 组成 Experience，补充描述和关系 | 第三阶段
竞赛与旅行模板 | 生成卡片、字段和穿插式时间线 | 第四阶段
智能收件箱 | OCR、EXIF、候选归类和批量确认 | 第五阶段
搜索与导出 | 全文检索、年度回顾、JSON 和 ZIP | 第六阶段
```

## 9. 已确定的第一版实施规格 {span=2}

第一版以本机或家庭服务器为中心。Web 页面负责上传和回看。手机通过分享入口把照片、文件或文字送入收件箱。指定文件夹或相册可以作为可选导入源。系统允许全部资料先进入，不要求上传时选择模板。

混合 AI 模式下，EXIF、哈希、文件类型、基础文本提取和本地索引优先在自己的设备上完成。云端 OCR、图像理解和候选归类做成独立开关，并且每次处理都记录处理方式、模型版本和结果来源。关闭云端 AI 后，资料仍然可以上传、搜索、建立经历和使用模板。

建议家庭服务器使用 Docker Compose。数据库、对象存储、任务队列、API 和 Web 前端分别使用独立服务，数据目录集中挂载到可备份磁盘。备份至少包含 PostgreSQL 数据库、对象存储原件、应用配置和导出清单。恢复测试要能在另一台设备上重新启动并读取资料。

## 10. 我建议先确认的产品选择 {span=2}

| 选择 | 我建议的默认值 | 需要你决定的原因 |
| --- | --- | --- |
| 部署方式 | 本机或家庭服务器 | 你希望资料掌握在自己的设备上 |
| 收集入口 | 网页拖拽、手机分享、快速文字、文件夹或相册导入 | 让资料及时进入统一收件箱 |
| AI 位置 | 混合模式，可关闭云端识别 | 平衡隐私、成本和识别效果 |
| 时间精度 | 支持不确定和时间区间 | 让旧经历可以自然录入 |
| 回顾方式 | 时间轴、全文搜索、模板卡片、自动回顾 | 覆盖浏览、查找和整理 |
| 初始范围 | 全部资料先接收，不强制分类 | 符合你不想四处归档的初衷 |
| 导出格式 | JSON 加原文件 ZIP | 决定资料能否长期带走 |

> [!TAKEAWAY] RecallSoro 应该是一个“先收集，后整理，按需回看”的个人经历总台账。竞赛和旅行只是模板，真正稳定的核心是统一收件箱、原始资料、经历关系、时间轴和可迁移导出。
