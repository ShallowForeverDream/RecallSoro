## 2. 旧资料管理器中值得保留的设计原则

原项目 `D:\MY_PROJECT\ZJH_TOOLS\personal-materials-manager`（后续会清理）已有一套经过实际使用的竞赛资料管理方式。以下原则直接吸收到 RecallSoro：

1. **不根据文件名或赛事名猜日期**：日期不详就是不详，排序时放最后。
2. **完全相同内容不重复存储**：用 SHA-256 判定重复，只增加来源记录。
3. **不修改原始文件**：所有导入都是副本，原件保持不动。
4. **不自动监视和回写源文件**：避免后台任务悄悄改变用户资料。
5. **本地处理优先**：OCR、缩略图、索引都在本机完成，不依赖云服务。
6. **保留编辑历史**：每次改动前保存旧版本，可恢复字段。
7. **归档优先于删除**：删除入口要克制，避免误删原件。
8. **分组与状态解耦**：主题分组独立于资料类型和核对状态。
9. **搜索覆盖多个字段**：名称、备注、附件名、OCR 文字都要可检索。
10. **导出不自动脱敏**：原件可能含身份证号、学号、签名和二维码，必须提示用户。

## 3. 已完整取用的会话调研成果

该会话派出 7 路子代理，通过 `gh api` 逐库核实了 PKM、图片档案/DAM、AI 记忆层、自托管台账库、奖项证书履历、时间线简历、物品书签台账七个方向的开源项目。完整表格和结论已沉淀到 `docs/research/open-source-research-full.md`，原始数据保留在 `personal-ledger-open-source.json`。

关键结论：

- 通用照片/DAM 工具缺“证书编号、获奖人、等级”这类业务字段，因此 RecallSoro 必须自己建模结构化经历。
- AI 记忆层里“Markdown 为真相源 + local-first + 用户自有”的形态最接近个人经历台账。
- NocoDB、Baserow、SQLPage 证明表格化台账可行，但对个人全经历场景过重，RecallSoro 保持轻量本地应用。
- 竞赛奖状台账没有完全对口的开源成品；Open Badges 的数据模型和证书验真思路值得借鉴。

- 文件名里的日期只作为低置信度线索，不自动设为事件日期。

- 归档优先于删除，解除关联不删除原件。

旧项目 README 和日期排序实现已归档到 `docs/research/legacy/`，随后删除原项目目录。

## 5. 迁移到 RecallSoro 后的变化

旧项目是“竞赛资料管理器”，数据落在 SQLite，依赖本地 Python 服务。RecallSoro 把它推广为“全部个人经历台账”，改为：

- Tauri 桌面应用，无独立服务进程。
- 数据保存在应用内的 IndexedDB，原件以 Blob 保存。
- 竞赛只是模板之一，旅行、项目、课程和年度回顾共用同一套 Capture/Experience 模型。
- 导出使用 ZIP（元数据 JSON + 原件），保证可迁移。
